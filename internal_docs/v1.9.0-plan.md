# PHP SimpleQueue v1.9.0 Roadmap & Implementation Plan

> Status: Exploration & planning — broad improvement roadmap, no single feature champion yet
> Target Release: v1.9.0
> Baseline: v1.8.0 (small & lightweight consolidation: 0 production duplicate windows, docs overhaul)
> Theme: Selective feature breadth + operational depth. Land a curated subset of the deferred
> capability areas, and harden the observability, administration, performance, and testing story
> across the board.

---

## Why this roadmap

v1.8.0 delivered the project's "small, lightweight" promise as a consolidation release: production
duplicate windows dropped from 37 to **0**, test duplicate windows fell from 1,424 to 1,014, the
docs were restructured around user/integrator/maintainer audiences, and every static gate
(PHPStan Level 9 + strict rules, PHPCS, quality ratchet) is green. Coming out of that release the
codebase is small, safe to change, and well documented — which is exactly the right point to reopen
capability planning.

There is no single champion feature for v1.9 yet, so this roadmap treats the release as a
**breadth + depth program**: it selects a small, coherent subset of the features deferred from
v1.7/v1.8 (middleware, typed worker events, dead-letter administration, job metadata) and pairs it
with cross-cutting hardening in observability, failed-job operability, performance validation, and
test/contract coverage. This is deliberately not "everything deferred lands at once" — multi-queue
workers and a full CLI runner remain too large and are deferred again below.

### Grounding findings from the v1.8.0 codebase

1. **Worker events are a string/array vocabulary, not typed.** `Worker` emits
   `claimed`, `completed`, `retried`, `failed`, `lost_ownership`, and `infrastructure_failure`
   through a single `emit(string $event, array $data)` into one opt-in callable
   (`setEventListener()`). `WorkerLoopFailureHandler` adds an `infra_error` event. Payload
   shapes are documented only in PHPDoc and drift risk grows as the vocabulary expands. This is the
   natural seam for a typed event vocabulary (and optional PSR-14 dispatch).
2. **Administration exists but stops at the storage row.** `JobStorageAdminInterface` provides
   `list()`, `count()`, and `pruneCompleted()`, and `JobDispatcher` exposes `getStatus()` /
   `cancelJob()`. There is no dead-letter concept, no retry/backoff inspection, and no way to
   operate on a failed job (re-queue, inspect error, purge). Failed jobs are terminal rows with an
   error string and nothing above them.
3. **The handler boundary is a single method.** `JobHandlerInterface::handle(int, array, ?callable)`
   leaves cross-cutting concerns (auth, logging, metrics, validation, retry policy) to the handler
   author. There is no execution context, no before/after hook, and no way to wrap a job centrally.
4. **The quality baseline is clean and the inventory is small.** Production is 57 classes / 282
   methods / 6,156 lines with **0** duplicate windows; tests are 398 methods / 6,830 lines with
   1,014 duplicate windows. The ratchet enforces 15/15/3 per method and frozen class sizes, so any
   new feature must be built to stay within those bounds or the ratchet must be re-baselined with
   a recorded, justified exception.
5. **Backend parity is a first-class constraint.** Redis, Database, and InMemory drivers, plus PDO
   and InMemory storage, must stay behaviorally identical. Any new capability (events, dead-letter,
   middleware) must be designed so all backends can implement it, or explicitly scoped per backend
   and documented in `docs/backend-parity.md`.
6. **Performance is measured, not assumed.** The benchmark harness (`benchmarks/run.php`) and
   operation-count checks exist and were extended in v1.7/v1.8. New features must land with a
   before/after profile and must not regress the documented roundtrip/throughput baselines.

## Release Intent

1. **Middleware & execution context (curated deferred feature)**: introduce
   `JobMiddlewareInterface` and `JobContextInterface` so users can wrap job execution with
   cross-cutting logic (metrics, logging, auth, validation, retry policy) without touching the
   handler. Backward compatible: the existing single-handler path stays the default; middleware is
   additive and registered on the registry/worker.
2. **Typed worker event vocabulary**: introduce a small set of typed event value objects that
   formalize the current string/array event payloads (`claimed`, `completed`, `retried`, `failed`,
   `lost_ownership`, `infrastructure_failure`), with the string/array listener kept as a thin
   compatibility shim. Optional PSR-14 dispatch is evaluated but not required (see Non-Goals).
3. **Dead-letter & failed-job administration**: add a `FailedJobAdminInterface` / admin manager
   that can list, inspect, re-queue, and purge failed jobs, plus an optional dead-letter retention
   policy. This converts terminal `failed` rows into an operable surface instead of a dead end.
4. **Observability & operability hardening**: structured event data with stable keys, failure
   telemetry, and guidance on monitoring failed jobs and dead-letter backlogs in `docs/operations.md`.
5. **Performance & reliability validation**: re-run and re-publish the benchmark profile for the
   new feature paths, confirm no regression in existing roundtrip/throughput baselines, and add
   fault-injection coverage for middleware failures and dead-letter promotion.
6. **Quality, testing & documentation**: expand contract tests for the new capability
   interfaces, keep every method under 15/15/3, keep PHPStan Level 9 / PHPCS clean with no new
   suppressions, and re-baseline `docs/backend-parity.md`, `docs/failure-matrix.md`,
   `docs/performance.md`, and `docs/upgrading.md` for v1.9.

## Architectural Principles & Constraints

- **Strict Type Safety**: `declare(strict_types=1)` on every file, PHPStan Level 9 with
  `strict-rules`, no new suppressions.
- **Framework Agnostic**: zero required runtime dependencies beyond `psr/container` and `psr/log`;
  Redis, PDO, and PSR-14 remain optional.
- **Backward Compatibility**: no signature changes to existing public interfaces
  (`JobStorageInterface`, `QueueDriverInterface`, `JobHandlerInterface`). New capability ships as
  new interfaces and additive methods/injection points, never by modifying existing required
  signatures.
- **In-Memory Parity**: every new capability must keep `InMemoryJobStorage` /
  `InMemoryQueueDriver` behaviorally identical to the real backends, and all backends must implement
  new capabilities or explicitly document their scope.
- **Quality Ratchet**: cognitive complexity <= 15, cyclomatic complexity <= 15, nesting depth <= 3,
  no new duplicate windows without a recorded exception, and existing class sizes must not grow.
  New classes stay within the 500-line target. If a feature genuinely needs a larger method/class,
  it must be sent through `quality/ratchet-exceptions.json` with a documented reason — the default
  is to decompose instead.
- **Modern PHP 8.2+ Only**: minimum PHP is 8.2, so no PHP 8.3+ language features (for example
  `#[Override]`, typed class constants). `readonly` classes, backed enums, and standalone
  `true`/`false`/`null` types are in scope.
- **Optimize Only With Evidence**: no speculative performance work; any benchmark change must come
  from a profiled, measured win.
- **De-duplicate With Judgment**: shared helpers must reduce real duplication and keep scenario
  intent visible (v1.6/v1.8 principle). Do not force unrelated code into shared bases purely to
  move a metric.

## Definition of Done

- [ ] Middleware pipeline ships with `JobMiddlewareInterface`, `JobContextInterface`, and a working
      default (no-op) path; the existing no-middleware worker path is unchanged and fully tested.
- [ ] Typed worker event vocabulary ships with value objects for every current string event; the
      string/array `setEventListener()` path remains functional as a compatibility shim.
- [ ] Dead-letter / failed-job administration ships with `FailedJobAdminInterface` and an
      `AdminManager` (or equivalent) supporting list, inspect, re-queue, and purge across all
      backends; failed jobs remain operable instead of terminal.
- [ ] All new capability interfaces are covered by contract tests across Redis, Database, and
      InMemory backends; `composer check` passes (PHPUnit, PHPStan Level 9, PHPCS, quality ratchet)
      with no new suppressions.
- [ ] The benchmark profile is re-run and re-published for the new paths with no regression in
      existing roundtrip/throughput baselines; operation-count checks cover the new paths.
- [ ] Fault-injection characterization tests cover middleware exceptions, dead-letter promotion,
      and event-listener failures.
- [ ] `docs/backend-parity.md`, `docs/failure-matrix.md`, `docs/performance.md`,
      `docs/upgrading.md`, `docs/operations.md`, `README.md`, and `CHANGELOG.md` are updated for

## Scope and Ordering

### Stage 1 — Middleware & Execution Context

**Goal**: add a central, optional interception point around job execution without coupling the
library to a framework or changing the existing no-middleware path.

#### Key Tasks

- [x] **M1 — Contracts**: design `JobMiddlewareInterface` (before/after/around job execution) and
      `JobContextInterface` (typed access to job id, type, payload, queue, attempts, and a
      `proceed()`-style continuation). Add PHPDoc with `@param`/`@return` on every method.
- [x] **M2 — Registry/injection point**: allow middleware to be registered on `JobRegistry` (or a
      new `JobMiddlewareRegistry`) and have `Worker` resolve and apply it around handler execution.
      Keep the no-middleware path as the default and verify it is behaviorally identical to v1.8.
- [x] **M3 — Ordering & failure semantics**: define and document deterministic middleware ordering
      (registration order), what happens when a middleware throws (propagate to the existing retry/
      fail path), and how the execution context is populated before the handler runs.
- [x] **M4 — Backend parity**: middleware is a pure worker-layer concern (no storage/driver
      changes), so it must behave identically across Redis, Database, and InMemory backends. Add
      contract tests exercising the middleware around a real claim/complete cycle on each backend.
- [x] **M5 — Docs & examples**: document middleware usage in `docs/extending.md` and add a runnable
      example in `examples/`.
---

### Stage 2 — Typed Worker Event Vocabulary

**Goal**: formalize the current string/array events into typed value objects so payload shapes are
enforced and stable, while keeping the existing callable listener working.

#### Key Tasks

- [x] **E1 — Event catalog**: enumerate the current events (`claimed`, `completed`, `retried`,
      `failed`, `lost_ownership`, `infrastructure_failure`, `infra_error`, and `backoff`) and
      define one typed value object per event with `readonly` properties and a
      `fromArray()`/`toArray()` factory pair (mirroring the `JobData` value-object pattern).
- [x] **E2 — Emitter refactor**: change `Worker::emit()` to dispatch typed event objects; keep the
      string/array callable listener as a thin shim that calls `toArray()`. Preserve the existing
      event names and payload keys exactly for backward compatibility.
- [x] **E3 — PSR-14 evaluation**: evaluate an optional `psr/event-dispatcher` integration behind a
      capability boundary (as with Predis/PDO). PSR-14 is not included because the existing
      callable listener is the compatibility surface and adding a dispatcher dependency would
      expand the runtime dependency surface without a required library guarantee.
- [x] **E4 — Observability test**: extend `WorkerObservabilityTest` to assert the typed event
      payload contracts (stable keys, no `Throwable`/stack data in log contexts) for every event
      type.
- [x] **E5 — Docs**: document the typed event vocabulary and listener shim in `docs/operations.md`
      and `docs/type-safety.md`.

---

### Stage 3 — Dead-Letter & Failed-Job Administration

**Goal**: give operators a way to act on failed jobs instead of treating `failed` as a dead end.

#### Key Tasks

- [x] **A1 — Contracts**: added framework-agnostic `FailedJobAdminInterface` and `AdminManager`,
      plus the `SupportsFailedJobAdministration` storage capability. All public methods have
      PHPDoc and the manager composes storage with the queue notification driver.
- [x] **A2 — Storage support**: implemented guarded failed-job reset/delete operations on
      `PdoJobStorage` and `InMemoryJobStorage`. Re-queue resets attempts and terminal metadata
      before notifying; purge removes the failed row and uses `SupportsJobRemoval` to drop
      pending, delayed, and processing notifications. `pruneCompleted()` semantics are unchanged.
- [x] **A3 — Optional dead-letter retention**: no automatic max-backlog or age policy was added.
      The current schema has no separate failure timestamp/history, and `pruneCompleted()`
      intentionally excludes failed jobs; operators can purge explicitly through `AdminManager`.
- [x] **A4 — Backend parity & contract tests**: added failed-job administration contract coverage
      for in-memory and SQLite/PDO storage, with queue notification assertions and parity updates
      in `docs/backend-parity.md`.
- [x] **A5 — Failure matrix**: documented successful and partially failed re-queue/purge paths in
      `docs/failure-matrix.md` and added deterministic notification fault-injection coverage in
      `tests/Integration/FailedJobAdministrationTest.php`.
---

### Stage 4 — Performance & Reliability Validation

**Goal**: prove that Stages 1–3 do not regress the documented performance profile and behave
correctly under failure.

#### Key Tasks

- [ ] **P1 — Benchmark baseline**: re-run `composer benchmark` on the v1.8.0 baseline, then after
      Stages 1–3; publish the before/after in `docs/performance.md` and confirm no regression in
      roundtrip/throughput baselines.
- [ ] **P2 — Operation-count checks**: extend `benchmarks/operation-count-checks.php` to cover the
      middleware path (no extra driver roundtrips) and the dead-letter re-queue path (bounded
      roundtrips).
- [ ] **P3 — Fault injection**: add deterministic tests for middleware throwing during execution,
      dead-letter promotion racing a claim, and event-listener exceptions being swallowed without
      breaking job completion.
- [ ] **P4 — Soak/load**: extend the worker soak/load scenarios (if feasible) to include a
      middleware-enabled worker and a dead-letter backlog to confirm no unbounded memory/CPU growth.

## Deferred beyond v1.9

The following areas remain deferred; each is too large to land safely together with Stages 1–3 in a
single release immediately following a consolidation release:

- multi-queue workers and queue-selection strategies (strict priority, round robin, weighted
  random, multi-key blocking dequeue);
- the full `bin/simplequeue` CLI runner (supervisor, worker management, job inspection);
- job metadata / tags on the storage row (schema change) — revisited only if a schema migration can
  be additive and backward compatible;
- mandatory PSR-14 event dispatch (evaluated in Stage 2, kept optional unless it lands cleanly).

v1.9 ships the internal boundaries (typed events, middleware seam, failed-job administration) that
make these later features safer, but it must not ship dormant public APIs that are not yet used.

---

## Explicit Non-Goals for v1.9

- Landing every deferred feature at once; v1.9 is a curated breadth + depth release, not a
  "kitchen sink" release.
- Dropping PHP 8.2 support or raising the minimum PHP version; using PHP 8.3+ language features.
- Adding hard external runtime dependencies to `composer.json` (`require`); PSR-14 stays optional.
- Breaking changes to existing public interfaces, constructor behavior, or database schemas.
- Schema changes to the `background_jobs` table unless fully additive and backward compatible
  (job metadata/tags are deferred).
- Forcing unrelated code into shared base classes, traits, or utilities purely to move a quality
  metric.
- Speculative performance work without a measured before/after profile.
- Rewriting the docs into marketing copy; every guide stays technical and actionable.
   `docs/performance.md`, and `docs/upgrading.md` for v1.9.
